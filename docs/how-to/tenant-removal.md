# Removing a tenant

mksrv has **no command that removes a tenant**. Deleting `tenants/<id>.yaml` only
removes what Terraform manages; everything `mksrv tenant apply` created stays.
This is the manual procedure.

> **Status: written from the code, never executed.** The first removal is its
> verification: correct this page as you go. Every step that deletes data needs
> the operator's confirmation, one at a time. Nothing here can be undone, except
> by restoring a backup.

## Scope

Written for a tenant with the stacks `database` and `openbao`, `storage:`, no
`dns_override`, no `web:`, no `mail:`, no PostgREST, no `cache` and no `files`:
the shape of a throwaway tenant. A tenant with any of those has more to remove
(DNS records, SES identity, mailboxes, edge vhosts, containers, Redis user,
file volumes) and **this page does not cover it**.

Below, `<id>` is the tenant, `<env>` the deployment's `env`.

## What a tenant leaves behind

| Where | What | Removed by |
|---|---|---|
| AWS | S3 bucket and its settings, IAM user, policy and access key | Terraform (step 3), once the bucket is empty |
| Postgres | `db_<id>`, role `<id>_login`, declared service roles | Hand (step 5) |
| Keycloak | Realm, its clients and users | Hand (step 6) |
| Edge disk | Login theme `themes/mksrv-<id>` | Hand (step 6) |
| OpenBao | KV entries, policies, AppRoles `tenant-<id>`, `svc-<id>`, `svc-<id>-<name>`, auth mount `oidc-<id>`, Transit key `<id>` | Hand (step 7) |
| Headscale | User `<id>`, its nodes and keys | Hand (step 8). The ACL rules go with step 4 |
| SSM | Passwords and AppRole ids | Hand (step 9) |
| Backup job, VPN broker roster | The tenant's database and realm in their lists | Regenerated by step 4 |
| Backups | Dumps, realm exports, Raft and volume snapshots | They **expire**, see the last section |

Left in place on purpose: the cluster-wide `mksrv_*` roles, and a harmless pgAdmin
server entry that you can delete in pgAdmin.

## Before you start

- Write down the tenant's `stacks`, `storage` and bucket name: you need them
  after the file is gone.
- Confirm there is nothing to keep. If there is, take a dump and copy the objects
  first.
- Web SSO gates get a port from the tenant's **position in the sorted tenant
  list**. If any tenant that sorts after `<id>` uses `sso: true`, adding or
  removing `<id>` moves its port: apply every such tenant in step 4 too, or stop
  and think. PostgREST ports are pinned in `mksrv.lock` and do not move.

## Steps

### 1. Stop the application and cut its credentials

On the tenant's node, stop its units. Then revoke every SecretID:

```bash
mksrv tenant secret-id <id> --approle <name> --list
mksrv tenant secret-id <id> --approle <name> --revoke <accessor>
```

### 2. Empty the bucket (irreversible: tenant buckets are not versioned)

With operator AWS credentials; the tenant's own key cannot delete.

```bash
aws s3 ls s3://<bucket> --recursive --summarize   # read it first
aws s3api list-multipart-uploads --bucket <bucket>
aws s3 rm s3://<bucket> --recursive
```

Abort any multipart upload the second command lists.

### 3. Remove the declaration and the infrastructure

Delete `tenants/<id>.yaml` and `tenants/<id>.users.yaml` from the workspace, then:

```bash
mksrv validate
mksrv plan --infra-only
```

For the shape above, expect to destroy **only** `<id>`'s resources: the bucket,
its public-access block, ownership controls, encryption, policy and lifecycle
(plus CORS if it declared origins), and the IAM user, its policy and its key. If
the plan touches anything else, stop. Then `mksrv apply --infra-only`.

### 4. Regenerate the fleet-wide lists, before deleting any data

The backup job dumps every database and exports every realm in a list that only
`tenant apply` rewrites. Delete the database or the realm first and the next
backup run fails.

Apply **one** remaining tenant that consumes `openbao`:

```bash
mksrv tenant apply <other-id>
```

This rewrites the Headscale ACL, the backup environment, the VPN broker roster and
the operator's OpenBao policy from the tenants that are left. It does not ask for
confirmation, and it **restarts Keycloak** and the VPN broker (a short sign-in
interruption for every tenant), restarts the selected tenant's PostgREST if it has
one, and rotates the broker's Headscale API key. Pick the tenant and the moment
accordingly.

Check that the backup environment on the backup host no longer lists `db_<id>` or
the realm.

### 5. Postgres

On the Patroni **leader** (`sudo podman exec mksrv-patroni patronictl -c /etc/patroni/patroni.yml list`), as the superuser (password in SSM,
`/mksrv/<env>/postgres/superpass`; type it at the prompt, never on the command
line):

```bash
sudo podman exec -it mksrv-patroni psql -U postgres -W
```

```sql
\l db_<id>
DROP DATABASE "db_<id>" WITH (FORCE);
DROP ROLE "<id>_login";
-- plus one DROP ROLE per declared service role
```

### 6. Keycloak

In the admin console (realm `master`), delete the realm `<realm>`. On the identity
host:

```bash
sudo ls -d /var/lib/mksrv/stacks/identity/themes/mksrv-<id>
sudo rm -r /var/lib/mksrv/stacks/identity/themes/mksrv-<id>
```

### 7. OpenBao

On the leader, in a root shell, with the root token read from SSM into the
environment without echoing it:

```bash
read -rs BAO_TOKEN; export BAO_TOKEN
bao() { podman exec -i -e BAO_ADDR=http://127.0.0.1:8200 -e BAO_TOKEN mksrv-openbao bao "$@"; }

bao kv list kv/tenants/<id>
bao kv metadata delete kv/tenants/<id>/<name>     # once per name listed, dev/ included
bao delete auth/approle/role/tenant-<id>
bao delete auth/approle/role/svc-<id>
bao delete auth/approle/role/svc-<id>-<name>      # once per declared AppRole
bao policy delete tenant-<id>-admin
bao policy delete tenant-<id>-dev
bao policy delete svc-<id>
bao policy delete svc-<id>-<name>
bao auth disable oidc-<id>
bao write transit/keys/<id>/config deletion_allowed=true
bao delete transit/keys/<id>
unset BAO_TOKEN
```

Deleting the Transit key makes anything encrypted with it unreadable, copies in
backups included.

An AppRole removed from the YAML of a tenant that **stays** is also left behind:
use the `delete` lines for that role and its policy.

### 8. Headscale

Log the tenant's node out of the tailnet (`tailscale logout`) and uninstall the
deploy agent. On the identity host (check the flags with `--help`, they change
between Headscale releases):

```bash
sudo podman exec mksrv-headscale headscale nodes list
sudo podman exec mksrv-headscale headscale nodes delete --identifier <node>
sudo podman exec mksrv-headscale headscale users destroy --name <id>
```

If the tenant ran on **another** tenant's node, leave the node alone.

### 9. SSM

```bash
aws ssm describe-parameters --query 'Parameters[].Name' --output text | tr '\t' '\n' | grep -F "<id>"
```

Read the list: a short `<id>` can match another tenant's names. The ones this
shape creates, under `/mksrv/<env>/`:

- `database/tenant_<id>_password` (and `tenant_<id>_svc_<role>_password`)
- `openbao/approle_<id>_role_id`, `approle_<id>_secret_id`, `approle_<id>_svc_role_id`
- `storage/tenant_<id>_s3_access_key_id`, `tenant_<id>_s3_secret_access_key`

## Verify

- `mksrv validate` passes and `mksrv plan --infra-only` reports no changes.
- No `db_<id>` in `\l`, no role starting with `<id>_` in `\du`.
- The realm answers 404; `bao auth list` and `bao policy list` do not name `<id>`.
- `headscale users list` does not show it.
- The next backup run succeeds.
- Commit the workspace change.

## What survives, and for how long

The data is not gone when the steps end. The restic job keeps 7 daily, 4 weekly
and 6 monthly snapshots, so dumps, realm exports and OpenBao Raft snapshots can
hold the tenant's data for about **six months**; volume snapshots are kept up to
30 days ([volume snapshots](volume-snapshots.md)). If data must disappear
sooner, that is a separate decision, because those snapshots hold every tenant.
