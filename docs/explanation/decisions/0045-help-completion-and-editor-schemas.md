# ADR 0045: Command help, shell completion and editor schemas, in three phases

- Status: Proposed (no code yet; each phase is its own change)
- Date: 2026-11-21

## Context

How the CLI helps its user today, checked in the code on 2026-11-21:

- **Help** is generated by cobra from each command's definition (`Use`, `Short`, `Long`, flag
  descriptions). No command has an `Example:`. The root `Long` still says the commands "are added in
  milestones M1–M6", and they all exist. Mutually exclusive flags (`--approle` with `--service`) are
  checked by hand in the run function, not declared to cobra.
- **Shell completion** does not exist: the root command sets `DisableDefaultCmd: true`, so there is no
  `mksrv completion`, and there is no `ValidArgsFunction` or flag completion anywhere. `mksrv deploy <TAB>`
  suggests nothing, nor `--stack <TAB>`.
- **Editor help for the YAML** is weak. The engine's schemas (`schemas/*.json`) enumerate only the DNS
  provider, the host provider and a protocol. `hosts[].stacks` and `hosts[].instance_type` are only a
  regular expression, so an editor cannot suggest the 19 stacks or the instance types. `mksrv init` does not
  write the `# yaml-language-server: $schema=…` header. A workspace that wanted form help ended up with a
  **hand-adapted copy** of the deployment schema (different wording, no `if/then/else`), already about 40 %
  larger than the engine's and referenced by nothing: a fork that drifts.
- The values to suggest are **already in the binary**: the stack catalog is embedded (`//go:embed all:stacks`)
  and the instance-type table lives in `internal/model/capacity.go`.

## Decision

Three layers, delivered **one phase at a time, in this order**: B, then A, then C. Each phase is a separate
change, mergeable and useful alone.

### Phase 1 — B: the schema comes from the binary, with real enums

- A new command `mksrv schema <deployment|tenant|stack|users>` prints the **effective** JSON Schema: the
  embedded base schema with values injected at run time from the embedded sources — `hosts[].stacks` items
  become an `enum` of the catalog's stack names (and a tenant's `stacks`, only the tenant-consumable ones),
  `instance_type` an `enum` of the types in the capacity table — plus a `description` (and
  `markdownDescription`) on the fields people look up most.
- `mksrv init` writes the files it scaffolds with the header
  `# yaml-language-server: $schema=<path>` and refreshes `.mksrv/schemas/<name>.json` (that directory is
  already disposable, regenerated state). `mksrv validate` refreshes the same files and, for a file with no
  header, prints a one-line hint. **It never edits a user's file.**
- The schema therefore always matches the installed binary, and a hand-maintained fork is no longer needed.
- **Acceptance:** the generated schema is valid; the synthetic example workspace validates against it; the
  stack `enum` equals the catalog (a test fails when a stack is added without being suggested); a typo in a
  stack name is flagged by an editor using the schema as well as by `validate`.

### Phase 2 — A: shell completion and better `--help`

- Remove `DisableDefaultCmd`, so `mksrv completion bash|zsh|fish|powershell` exists.
- **Dynamic completion** read from the workspace (found the same way as for any command, silently empty
  when there is none): tenant ids (`tenant apply <TAB>`, `users apply`, `tenant secret-id`), host names
  (`deploy <TAB>`), stack names (`--stack <TAB>`), a tenant's `storage.approles` names (`--approle <TAB>`),
  and a mail alias or mailbox where a command takes one.
- `Example:` on the commands people run most; declare exclusive flags with `MarkFlagsMutuallyExclusive`; fix
  the stale root text.
- **Acceptance:** completion never prints an error or blocks without a workspace; a test per completer; the
  generated scripts are produced by the CLI and not committed.

### Phase 3 — C: insertable templates

- `defaultSnippets` in the generated schema: a whole host block, a tenant skeleton, and the blocks people
  copy most (`web`, `mail`, `storage`, `database.service_roles`), so typing the block name inserts a complete,
  valid starting point.
- **Acceptance:** each snippet, instantiated, passes `validate`.

## Alternatives considered

- **Keep hand-maintained schema copies.** This is what drifted. Rejected.
- **Generate the schema from the Go types by reflection.** The engine's schemas carry rules a struct tag
  cannot express (`if/then/else`, cross-field constraints) and `validate` already depends on them; replacing
  them is a larger and riskier change. We patch the existing schema at run time instead.
- **Our own language server.** Far more to build and maintain than a schema, for the same suggestions.
- **A form UI.** The reason the fork exists; out of scope here.

## Consequences

- The suggestions track the installed binary: upgrading mksrv upgrades the editor's help.
- The new command and the generated files add a small surface to keep in step with the catalog; the
  acceptance tests above exist for that.
- Completion reads the workspace on each TAB, so it must stay fast and must fail quietly.

## Not verified

That a given editor honours the schema header and the enums (the YAML language server in the common editors
does; no editor was tried), how many instance types the capacity table holds, and whether the tenant,
stack and users schemas follow exactly the same pattern as the deployment schema.
